# Idempotency

## One-liner
The same operation, repeated, produces the same result: no duplicates, no side effects.

## Symptoms
- Retries produce duplicates.
- At-least-once delivery.
- Processes get re-executed.

## Solution
- An idempotency key per operation (a client-generated ID).
- The key is stored; a repeated key returns the stored result.
- The operation is applied once, no matter how many times it is called.
- The key is part of the API, not an implementation detail.

## When to use
- The operation may be retried.
- Duplicates are unacceptable.
- Instead of: "we hope the client does not retry".

## When NOT to use
- At-most-once is acceptable.
- Read-only operations.
- The operation is cheap and duplicates are harmless.

## Trade-offs
- vs a one-shot: a key vs a call.
- vs a distributed ID: a client key vs a server key.
- vs a database constraint: a key vs a unique index.

## Common pitfalls
- A key that is generated by the server (the client cannot retry).
- A key that is not stored (the dedup is a lie).
- A key that is reused across different operations (the dedup is wrong).
