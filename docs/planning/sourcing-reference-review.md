## Product distinction

The reference is a Laravel12/PHP8.2, Blade/Livewire3 sourcing operations application. Its client requests are handled by assigned administrators; quotations, payment evidence, sourcing routes, destinations and carrier tracking extend into logistics. ProcureFlow is a Spring Boot/React organization-to-organization procurement application with independent buyer/supplier grants, multiple supplier responses, currency-separated comparison, atomic award, fulfillment and receipt.

The common request → quotation → order spine makes the reference useful. Agent assignment, payments, shipment services and refund administration are additional business domains, not missing pieces of ProcureFlow's accepted requirements. Keep ProcureFlow's modular monolith and tenant boundaries.

## FSB-first proposal after owner steering

Additional source inspected: `app/Livewire/Admin/SourcingOrderWorkflow.php` on the supplied branch. Its order component owns current status, available workflow changes, tracking inputs, parcel evidence and destination tracking together. Status update checks actor assignment and allowed transition, reports a visible error and restores current status on rejection. This reinforces two useful patterns: make the current stage obvious, and place permitted next actions beside it. ProcureFlow can apply those patterns through its existing `OrderView.history` and `allowedActions`, without adopting FSB's China/UAE/carrier/payment workflow.

**Proposed first delivery: workspace status cards and order progress.** This is a draft, not implementation or release evidence.

1. Replace the operational queue's plain status-count list with clickable status cards. Each card shows a friendly status label and the server aggregate count, and opens that existing queue filtered to the selected status. Clicking resets page to zero, retains title search/page size and visibly marks the selected filter. Include All statuses with the sum of the returned status counts. Counts cover the selected queue kind and title search, independent of selected status and loaded page. Keep an explanation so users do not mistake filtered counts for organization-wide statistics.
2. Use neutral status names: draft requests, sent requests, awarded requests; invitations awaiting quotation, draft quotations, submitted quotations, accepted quotations; created, confirmed, processing, dispatched and received orders. FSB's “Action required” idea inspires discoverability, but ProcureFlow must not infer that a sent RFQ has received a quote or that every visible order action belongs to the current user. Current aggregate DTOs do not carry that evidence.
3. On order detail, add a five-stage progress display: Created → Confirmed → Processing → Dispatched → Received. Describe completed/current/pending states in text, with `aria-current="step"` for the current stage, and retain the existing authoritative timestamped history. Future stages have no invented dates. Derive next-action buttons only from server `allowedActions`; keep dispatch/receipt review, whole-order semantics, request failure handling and duplicate-submit guards.
4. Group buyer, supplier, order reference, RFQ title, currency and subtotal into a readable order summary above the existing lines/terms. Keep original offer expiry clearly distinct from fulfillment progress. Preserve return-to-queue/analytics behavior and existing accepted data snapshot.
5. Keep the existing palette and buyer catalog-first entry. Reflow cards and stepper at390px; keyboard-visible focus and text labels carry state without relying on color. Use semantic buttons for filtering. Loading, empty, error/retry and expired-session behavior remain visible. No new dependency, database schema, API, provider or background job is needed for this slice.

Expected ownership: `frontend/src/features.js` owns queue filters/data and order rendering; `frontend/src/styles.css` owns card/stepper presentation. Generated backend static assets follow the existing frontend build. Existing WorkspaceService/WorkspaceQueryRepository/OrderViews own authorization, aggregates, snapshots and event history; do not duplicate those rules in a new frontend service. No entity/FK/relation changes.

Smallest sufficient proof before acceptance: (a) status cards use `statusCounts`, not `rows.length`, with a multi-page fixture; (b) status click updates filter/page and preserves title query/page size; (c) no forbidden kind for no-grant/single-grant users and no cross-tenant count exposure; (d) all five order states render correctly with only observed dates and permitted actions; (e) dispatch/receipt confirmation and stale-conflict/401 behavior remain intact; (f) keyboard/mobile rendering and native build pass. Existing backend behavior is reused, not reimplemented. Any new count, cross-record action inbox or delivery promise would need its own requirement.

Next FSB-derived candidates, after this bounded slice: guided product/specification request form, real product media, printable commercial record, and localization. Each requires separate scope and proof. Supplier scoring, approval chains, reusable templates and partial deliveries are ProcureFlow ideas, not findings established by this FSB inspection.
